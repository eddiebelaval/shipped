### OpenAI publishes its chip benchmark

OpenAI released the first performance results from Jalapeño, its custom inference chip designed with Broadcom, on August 25. The claim: on InferenceX, a public benchmark using GPT-OSS 120B, Jalapeño delivers more peak throughput per kilowatt and lower token latency than commercial systems in the comparison. The results held across DeepSeek R1 and Kimi K2 as well, so the gains are not model-specific. OpenAI says Jalapeño sits on the Pareto frontier of performance-per-watt and latency.

The mechanism: most inference hardware forces a tradeoff between throughput (tokens per second in aggregate) and latency (response time for a single user). Jalapeño, OpenAI says, handles both without the tradeoff. The benchmark is public, which means the claim is checkable. OpenAI chose to publish rather than keep the result internal.

The blast radius is slow-moving but large. If Jalapeño performs at scale what the benchmark shows in controlled testing, OpenAI's marginal cost of serving inference drops substantially. That changes unit economics, potentially before any revenue inflection from the ChatGPT product. Lower serving costs either widen margins or compress API pricing for customers. Both outcomes are meaningful for the broader market.

The pattern: every major frontier lab is now building custom silicon. Google has TPUs. Meta has MTIA. Anthropic runs on AWS Trainium and Inferentia. xAI built custom cluster infrastructure in Memphis. Custom silicon is the infrastructure moat of the next cycle, not because NVIDIA's hardware is bad, but because running on NVIDIA at frontier scale means paying NVIDIA's margins indefinitely. OpenAI just told NVIDIA, publicly, that it has a path off that dependency.

The builder's move: nothing actionable today. Jalapeño is internal infrastructure. But if this benchmark holds under production load, watch for API price adjustments in Q1. Note whether throughput gains translate to lower latency on the models you actually use.

### Claude Code 2.1.245: the wildcard warning

Claude Code shipped version 2.1.245 on August 25. The headline change is a startup warning for Bash allow rules that use a wildcard before the subcommand. A rule that allows `bash *` would trigger it. The intent is to surface rules that are more permissive than the author likely intended.

The mechanism: at session initialization, Claude Code now scans allow rules and logs a warning when a wildcard appears in the position before the subcommand. This catches a class of rules where the author intended to permit a specific bash invocation pattern but accidentally opened a wider permission.

The blast radius is narrow but the catch rate is meaningful. Overly permissive bash rules in Claude Code sessions are a real footgun, most common in project settings files where someone copied a rule without reading what the wildcard covered. Getting the warning at startup surfaces the problem before any agentic session runs with it.

Also in this release: a new Auto mode tab in /permissions for viewing and editing auto mode classifier rules; transcript rendering improvements; the context cost of loading the built-in claude-api skill dropped from 200k-plus tokens to roughly 25k, because the skill now loads reference docs on demand rather than pre-loading everything. That last change matters for long agentic sessions where persistent context costs accumulate.

The builder's move: update Claude Code. On first launch in any project, check the startup output for wildcard warnings. If you find one you do not remember writing, the warning is telling you something useful.
